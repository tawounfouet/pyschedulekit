# REL-07 — GitHub Release + Provenance

## Goal

Create a verifiable GitHub prerelease for the exact PyScheduleKit artifacts that have already passed:

1. release-candidate qualification;
2. TestPyPI publication and verification;
3. PyPI publication and verification.

The GitHub release is therefore the final distribution record for the same bytes, not a separate build.

## Release promotion chain

```text
vX.Y.Z tag
    ↓
REL-04 qualify
    ↓
build provenance attestation
    ↓
REL-05 TestPyPI
    ↓
verify TestPyPI
    ↓
REL-06 PyPI
    ↓
verify PyPI
    ↓
REL-07 GitHub Release
    ↓
re-download assets
    ↓
checksum + provenance verification
```

## Build provenance

For real pushed release tags, the qualification job generates a GitHub artifact attestation for the qualified wheel and source distribution.

The workflow uses the official GitHub action pinned to an immutable commit:

```text
actions/attest
@1e69f48acb82d1966a394da916b4c1698aa569d6
```

The qualification job receives only the permissions required by the current attestation API:

```yaml
permissions:
  contents: read
  id-token: write
  attestations: write
  artifact-metadata: write
```

The attestation is generated from:

```text
release-candidate-sha256.txt
```

which identifies the exact wheel and sdist produced by the tagged build.

Manual workflow-dispatch dry runs do not create release attestations.

## Production verification is a hard prerequisite

The GitHub release job declares:

```text
needs:
  qualify-release-candidate
  verify-pypi
```

Therefore GitHub Release creation cannot occur unless the production PyPI package has already been installed and smoke-tested successfully.

## Exact release assets

The GitHub release job downloads the retained artifact:

```text
release-candidate-dists-<tag>
```

and re-validates:

```bash
sha256sum --check release-candidate-sha256.txt
```

It then verifies the GitHub artifact provenance before creating the release.

No build command exists in the release job.

## Existing-tag requirement

The release is created with:

```text
--verify-tag
```

The GitHub CLI is therefore forbidden from creating an implicit tag.

The tag has already been validated by REL-04 and must exist remotely.

## Alpha release semantics

PyScheduleKit `0.1.0a1` is published as a GitHub prerelease:

```text
--prerelease
--latest=false
```

The release title is:

```text
PyScheduleKit 0.1.0a1
```

Release notes are generated from GitHub history through:

```text
--generate-notes
```

## Release assets

The release attaches exactly:

```text
pyschedulekit-0.1.0a1-py3-none-any.whl
pyschedulekit-0.1.0a1.tar.gz
release-candidate-sha256.txt
```

The wheel and sdist are the same bytes qualified, published to TestPyPI, and published to PyPI.

## Post-release verification

A separate verification job downloads the published release assets again.

It verifies:

```text
GitHub release tag                 ✅
GitHub release is not draft        ✅
GitHub release is prerelease       ✅
wheel downloaded                   ✅
sdist downloaded                   ✅
checksum manifest downloaded       ✅
SHA-256 checks pass                ✅
GitHub artifact provenance passes  ✅
```

The workflow therefore verifies the public release from the consumer side instead of trusting the upload step alone.

## Immutable Releases

Before the first real release tag, enable GitHub Immutable Releases for the repository.

With immutable releases enabled, publication locks:

```text
release tag
release assets
```

against later replacement or deletion while the release remains published.

GitHub also creates a release-level attestation for immutable releases, complementing the build provenance generated by `actions/attest`.

The recommended publication model is:

```text
create draft internally
    ↓
attach all assets
    ↓
publish
    ↓
release becomes immutable
```

`gh release create` follows this asset-upload flow internally when release assets are supplied in the create command.

## Two provenance layers

REL-07 deliberately creates two complementary trust records.

### Build provenance

```text
wheel/sdist digest
      ↓
workflow / repository / commit / event
      ↓
GitHub artifact attestation
```

This proves where the package artifacts originated.

### Immutable release provenance

When Immutable Releases is enabled:

```text
release tag
+ commit SHA
+ release assets
      ↓
GitHub release attestation
```

This proves the integrity of the published GitHub release record.

## Consumer verification

Build provenance can be checked with:

```bash
gh attestation verify \
  pyschedulekit-0.1.0a1-py3-none-any.whl \
  --repo tawounfouet/pyschedulekit
```

For immutable releases, consumers can additionally verify:

```bash
gh release verify v0.1.0a1

gh release verify-asset \
  v0.1.0a1 \
  pyschedulekit-0.1.0a1-py3-none-any.whl
```

## Workflow fitness tests

CI statically enforces that:

- tagged candidates generate build provenance;
- the attestation action is SHA-pinned;
- required attestation permissions are present;
- GitHub Release creation depends on successful PyPI verification;
- release assets come from the retained release candidate;
- checksums are validated before release creation;
- the release job contains no rebuild;
- `--verify-tag` is present;
- alpha releases use prerelease semantics;
- generated release notes are enabled;
- release assets are downloaded again after publication;
- checksums are revalidated after download;
- provenance is verified both before and after release creation.
